## Итог

- VMID: **100**, имя `REGUL-R500`
- Диск: `ide0: local-lvm:vm-100-disk-0,size=4G`
- Платформа: `machine: pc` (i440fx), `bios: seabios`, `ostype: other`
- Сеть: `net0` (управление, бывший NAT) — `pcnet` на `vmbr1` (рабочая LAN 192.168.1.x);
  `net1..net3` (внутренние сегменты, EtherCAT) — `pcnet` **без бриджа** (изолированы)
- Boot: `order=ide0`

Итоговый конфиг (`qm config 100`):

```
bios: seabios
boot: order=ide0
cores: 1
ide0: local-lvm:vm-100-disk-0,size=4G
machine: pc
memory: 2048
name: REGUL-R500
net0: pcnet=08:00:27:9A:B1:44,bridge=vmbr1
net1: pcnet=08:00:27:66:46:2E
net2: pcnet=08:00:27:7F:F3:F3
net3: pcnet=08:00:27:52:DD:C0
ostype: other
```

> ВАЖНО: `net0` должен смотреть в **рабочую** сеть. На этом хосте два моста:
> `vmbr0` → `enp1s0` (192.168.0.x, link down), `vmbr1` → `enp3s0` (192.168.1.x, активная).
> Если повесить все NIC на `vmbr0`, гость окажется в «мёртвой» сети и его не увидит
> ни AstraIDE, ни пинг. `net1..3` без бриджа дают предупреждения
> `tap100iN not attached to any bridge` — это нормально (изоляция).

## Важные особенности этого OVA

- OVA = tar-архив: внутри `.ovf` + `.vmdk` (+ `.mf`, не нужен).
- VMDK из VirtualBox — **streamOptimized**, импортируется только через конвертацию `qemu-img`.
- `qm importovf` на этом OVA падает: `referenced path '...-disk001.vmdk' is invalid`
  (относительная ссылка на диск не резолвится).
- Гость **QNX**: не понимает VirtIO/lsi. Нужны IDE-диск, NIC модели `pcnet`
  (в OVA — Am79C973), BIOS SeaBIOS, машина i440fx (`pc`), не q35.
- В OVA 4 сетевые карты: 1 x NAT (управление) + 3 изолированных сегмента
  (`innerETH0/1/3`, один из них EtherCAT). MAC-адреса сохранены из OVF.
- Загрузчик QNX v1.2b предлагает два образа: рабочий **`VirtualBox_VIRTUAL.ifs`**
  (в нём прошито `REGUL_BOARD=VirtualBox`, `REGUL_COM_MODULE=VIRTUAL`); второй,
  `REGUL_VirtualBox.ifs`, в QEMU/Proxmox не стартует — его не выбирать.
- **SSH/FTP/Pure-FTPd по умолчанию отключены** в `/etc/inetd.conf` (строки
  `#-ssh-disabled from runtime.cfg--#`, `#-ftp-disabled from runtime.cfg--#`).
  Включаются ключами `[PlcServices] EnableSSH=1` / `EnableFTP=1` в `runtime.cfg`
  (этот файл умеет править вендорская AstraIDE) — дальше `runtime_config_changed.sh`
  раскомментирует строки и делает `SIGHUP inetd`.
- В прошивке есть **демо-ограничение 24 часа**: `sleep 86400 && /scripts/codesys/stop_ham.sh &`
  в `/etc/init/VirtualBox/board-init.sh`; через сутки uptime гасится HAM и службы ПЛК
  (подробнее — в `Часть 2 «Карта файловой системы»`).
- Есть сервисное меню **«Tap to service»** (backup/mount разделов user/system,
  обновление с USB) — это GUI апплаенса, а не консоль; шелла там нет.

## Шаги

### 1. Сеть и DNS на хосте (были не настроены)

Симптом: `apt update` — `Temporary failure resolving`, `getent hosts` пусто.

Причина: default-маршрут висел на неактивном `vmbr0` (сеть 192.168.0.x, link down),
а реальная сеть 192.168.1.x — на `vmbr1` без шлюза. В `/etc/resolv.conf` первым
стоял `127.0.0.1` (локального резолвера нет).

Исправление в GUI: узел `pve` → System → Network — у `vmbr0` убрать Gateway,
у `vmbr1` добавить `192.168.1.1`; System → DNS — `192.168.1.1`, `8.8.8.8`,
`127.0.0.1` удалить.

Быстрая проверка/переключение без GUI:

```bash
ip route replace default via 192.168.1.1 dev vmbr1
printf 'search my.home\nnameserver 192.168.1.1\nnameserver 8.8.8.8\n' > /etc/resolv.conf
ping -c2 8.8.8.8 && getent hosts deb.debian.org
```

Скрипт переключения между двумя сетями (кабель переставляется физически):

```bash
cat > /usr/local/bin/net-select <<'EOF'
#!/bin/bash
case "$1" in
  0) GW=192.168.0.1; IF=vmbr0 ;;
  1) GW=192.168.1.1; IF=vmbr1 ;;
  *) echo "usage: net-select 0|1"; exit 1 ;;
esac
ip route replace default via "$GW" dev "$IF" onlink
printf 'search my.home\nnameserver %s\nnameserver 8.8.8.8\n' "$GW" > /etc/resolv.conf
ping -c1 -W2 "$GW" >/dev/null && echo "default via $GW ($IF) OK" || echo "no link on $IF?"
EOF
chmod +x /usr/local/bin/net-select
```

### 3. Копирование и распаковка OVA

```bash
# с рабочей машины
scp -o StrictHostKeyChecking=accept-new .\vm.ova root@192.168.1.125:/var/tmp/

# на хосте
cd /var/tmp && mkdir vm && tar -xf vm.ova -C vm
```

### 4. Конвертация диска и параметры из OVF

```bash
cd /var/tmp/vm
qemu-img info "REGUL_R500_71_W(1.7.2.6)-disk001.vmdk"
#   virtual size: 4 GiB, create type: streamOptimized
qemu-img convert -p -O qcow2 "REGUL_R500_71_W(1.7.2.6)-disk001.vmdk" disk.qcow2
grep -E 'Memory|VirtualQuantity' "REGUL_R500_71_W(1.7.2.6).ovf"
#   RAM 2048, CPU 1
```

### 5. Создание VM и импорт диска

```bash
qm create 100 --name REGUL-R500 --memory 2048 --cores 1 \
  --ostype other --machine pc --bios seabios \
  --net0 pcnet=08:00:27:9A:B1:44,bridge=vmbr1 \
  --net1 pcnet=08:00:27:66:46:2E \
  --net2 pcnet=08:00:27:7F:F3:F3 \
  --net3 pcnet=08:00:27:52:DD:C0

qm disk import 100 /var/tmp/vm/disk.qcow2 local-lvm
#   unused0: successfully imported disk 'local-lvm:vm-100-disk-0'
qm set 100 --ide0 local-lvm:vm-100-disk-0 --boot order=ide0
qm start 100
```

Консоль: веб-интерфейс → VM 100 → Console.

### 6. После успешного запуска

```bash
qm set 100 --onboot 1
```

`disk.qcow2` и распакованный vmdk **не удалять**, пока не проверено всё: это запасной
исходник для повторного импорта.

## Сети: два моста на хосте

```
vmbr0: enp1s0, 192.168.0.125/24  — сеть 192.168.0.x (сейчас link down)
vmbr1: enp3s0, 192.168.1.125/24  — рабочая сеть 192.168.1.x, gateway 192.168.1.1
```

- Управление Proxmox и гость — через `vmbr1`.
- `gateway` в `/etc/network/interfaces` должен быть только на активном мосте
  (переключается `net-select 0|1`, см. шаг 1).
- Для «внутренних» сегментов EtherCAT при желании сделать изолированные бриджи
  (`bridge-ports none`) и перевесить `net1..net3` на них.

## Сервисы SSH/FTP внутри гостя

По умолчанию `sshd`, `pure-ftpd` и `telnet` закомментированы в `/etc/inetd.conf`
(маркеры `#-ssh-disabled from runtime.cfg--#` и т.п.). Штатное включение — через
AstraIDE: `[PlcServices] EnableSSH=1` / `EnableFTP=1` в `runtime.cfg`
(`/mnt/user/codesys/etc/runtime.cfg`), после чего `runtime_config_changed.sh`
раскомментирует строки и перезапустит `inetd`.

- `sshd_config`: `PermitRootLogin yes`, `PasswordAuthentication yes`,
  `PermitEmptyPasswords yes`, `AllowUsers root`.
- В `/etc/shadow` у root стоит `*` — в QNX это «без пароля», т.е. вход root
  с пустым паролем (сразу после входа задать пароль командой `passwd`).
- FTP-учётки `plcuser`/`plclogs` в `ftp.userlist` имеют **пустой пароль**
  (`plcuser` — ReadWrite, home `/`; `plclogs` — ReadOnly, home `/logs`).

Если IDE нет под рукой, строку `ssh` в `inetd.conf` можно включить правкой на диске
(см. раздел «Правка файлов с хоста» в `Часть 2 «Карта файловой системы»`).

## Демо-ограничение 24 часа

`/etc/init/VirtualBox/board-init.sh` (46 байт, одна строка):

```sh
sleep 86400 && /scripts/codesys/stop_ham.sh &
```

Через 24 ч uptime `stop_ham.sh` делает `slay -f ham2` и убивает службы из
`/etc/regul/ham.entities`, т.е. ПЛК-рантайм останавливается (ОС и сеть живы).
Перезагрузка сбрасывает таймер. Снятие — изнутри QNX (закомментировать строку)
или байтовой правкой `&&` → `||`; детали в `Часть 2 «Карта файловой системы»`.

## Доступ к файловой системе гостя

Диск — QNX6 в одном MBR-разделе (тип `b1`, старт с сектора 63 → offset 32256).
Linux-драйвер `qnx6` **только для чтения**.

Предпочтительный способ (без nbd, VM выключена):

```bash
qm stop 100
lvchange -ay pve/vm-100-disk-0
mount -t qnx6 -o ro,offset=32256 /dev/pve/vm-100-disk-0 /mnt
ls -la /mnt
# ...
umount /mnt
```

Через nbd (если нужен именно блочный узел):

```bash
modprobe nbd max_part=8
qemu-nbd -c /dev/nbd0 -f qcow2 -r /var/tmp/vm/disk.qcow2   # или /dev/pve/vm-100-disk-0
sleep 1; lsblk /dev/nbd0
mount -t qnx6 -o ro /dev/nbd0p1 /mnt
umount /mnt; qemu-nbd -d /dev/nbd0
```

Грабли nbd (встречались на практике): `partprobe` в PVE нет; если не размонтировать
`/mnt` перед `qemu-nbd -d`, следующий `mount`/`grep` даёт `Input/output error`;
диск может подняться `RO=1` — тогда работать напрямую с LV (первый вариант) или
`blockdev --setrw /dev/nbd0`. Раздел не обязателен: всё можно делать по offset 32256.

- **Передача файлов внутрь:** ISO (только чтение) через CD-ROM, FAT-диск
  (QNX умеет `dosfs`), либо по сети (SSH/SFTP после включения).
- **Просмотр списка ФС:** `find /mnt -xdev -printf '%y %10s %TY-%Tm-%Td %TH:%TM %p -> %l\n'`
  (см. `regul-fs.txt`), `du -sh /mnt/*` (см. `regul-du.txt`).

## Типичные проблемы

| Симптом | Причина / решение |
|---|---|
| `referenced path '...vmdk' is invalid` | `qm importovf` не резолвит относительные пути VirtualBox → ручной импорт (шаг 4–5) |
| `name: invalid format` | имя VM проверяется как DNS-имя, `_` запрещён → `REGUL-R500` |
| `Temporary failure resolving` | DNS/шлюз на хосте (шаг 1) |
| VM не грузится, «no bootable device» | диск должен быть `ide0`, `boot order=ide0`, машина `pc`, BIOS SeaBIOS |
| BSOD/QNX не видит диск или сеть | диск не на virtio/lsi, NIC должна быть `pcnet` |
| Нет сети в госте | `net0` должен быть на `vmbr1` (рабочая LAN), а не на `vmbr0`; модель `pcnet` |
| Гость не виден в AstraIDE | `net0` не в рабочей LAN; AstraIDE требует Npcap и прав администратора (запуск от админа) |
| Порт 22 закрыт | `EnableSSH=1` в `runtime.cfg` не применён/`inetd.conf` остался закомментированным → см. `Часть 2 «Карта файловой системы»` |
| `Input/output error` на `/dev/nbd0p1` | `/mnt` не размонтирован перед `qemu-nbd -d`; nbd поднялся read-only → работать с LV напрямую |
| Консоль «не принимает ввод» | это GUI апплаенса (Photon), текстового шелла нет; `Ctrl+Alt+1..4` и `qm sendkey` не помогают — доступ только по сети |
| Через 24 ч ПЛК встал | демо-таймер `sleep 86400 && stop_ham.sh` в `VirtualBox/board-init.sh` |

# Часть 2. Карта файловой системы и сервисы

## Ограничение 24 часа (демо)

Найдено (файлы по 46 байт, ровно одна строка):

1. `/etc/init/VirtualBox/board-init.sh` — для нашей платформы (VirtualBox/VIRTUAL):
   ```sh
   sleep 86400 && /scripts/codesys/stop_ham.sh &
   ```
2. То же самое в `/etc/init/VMWare/board-init.sh` (для платформы VMware, у нас не используется).

Через **86400 секунд uptime** (24 ч с момента старта VM, не календарных суток — перезагрузка сбрасывает
отсчёт) запускается `/scripts/codesys/stop_ham.sh` (336 байт), который делает:

```sh
slay -f ham2                      # убить HAM (менеджер/служба CODESYS)
# убить процессы из /etc/regul/ham.entities (кроме espd|sysinfo|logger|gpiod)
/etc/init/sysinfo.sh stop
```

Т.е. после суток работы гасятся HAM и связанные службы ПЛК — это и есть демо-ограничение
(«non-commercial use only»), а не ограничение лицензии CODESYS как таковой.

HAM (High Availability Manager) — менеджер/супервизор служб рантайма: он поднимает и
сторожит процессы, перечисленные в `/etc/regul/ham.entities` (там же `espd`, `sysinfo`,
`logger`, `gpiod` и др.). После `slay -f ham2` перезапуска этих служб не будет до
перезагрузки: ОС, сеть, SSH/FTP и GUI-оболочка остаются живы, но ПЛК-рантайм стоит.
Вызывается таймер не из `system.main`, а через него: `system.main:147` запускает
`/etc/init/$REGUL_BOARD/board-init.sh`, т.е. при `REGUL_BOARD=VirtualBox` — тот самый
46-байтный файл.

Прочие вхождения `86400`/`stop_ham` — не ограничения:
`/etc/init/bl_crc_check.sh` (ежедневная пауза в цикле проверки CRC, штатно),
`/scripts/update_raw_nand.sh`, `/scripts/update/etfs-init.sh` (вызов stop_ham при обновлении прошивки, штатно).

Проверка:

```bash
grep -rn "86400\|stop_ham" /root/from-vm/etc /root/from-vm/scripts
cat /root/from-vm/scripts/codesys/stop_ham.sh
grep -n "board-init" /root/from-vm/etc/firmware_files.lst   # проверка целостности может ловить правку
```

Варианты нейтрализации:

- **изнутри QNX** (правильно): закомментировать/удалить строку в `/etc/init/VirtualBox/board-init.sh`
  (и в `VMWare/board-init.sh`) — единственный надёжный способ, длина файла не важна;
- **байтовая правка с хоста** (`dd`): заменить `&&` на `||` (та же длина, 2 байта):
  `sleep 86400 || /scripts/codesys/stop_ham.sh &` — sleep завершится успешно, stop_ham не выполнится;
  смещение `&&` = начало строки + 12;
- замена `86400` → `99999` (27,7 ч) только отодвигает срабатывание, не отключает.

Внимание: это ограничение демо-прошивки; снятие — на свой риск. Если `board-init.sh` входит в
`firmware_files.lst`/`.hash`, правка может быть замечена проверкой целостности прошивки.

## Механизм управления сервисами (inetd / SSH / FTP / SNMP / SQL)

`/etc/init/system.main` держит `fwatch` на `/mnt/user/codesys/etc/runtime.cfg` и при его
изменении запускает `/scripts/codesys/runtime_config_changed.sh`. Скрипт читает
`runtime.cfg` и управляет сервисами:

| Ключ в runtime.cfg | Что делает |
|---|---|
| `[PlcServices] EnableFTP=1` | раскомментирует `ftp` в `/etc/inetd.conf`, `SIGHUP inetd`; иначе — комментирует |
| `[PlcServices] EnableSSH=1` | то же для `ssh` |
| `[PlcServices] EnableSNMP=1` | `snmpd_control.sh start` / `stop` |
| `[PlcServices] EnableSQL=0` | стоп MySQL; иначе старт (по умолчанию стартует) |

Как именно правит: `sed -i "s/^ssh/#-ssh-disabled from runtime.cfg--#/1"` и наоборот,
то есть в `inetd.conf` состояние видно по маркеру `#-ssh-disabled from runtime.cfg--#`.
В текущем образе SSH/FTP/telnet выключены. Штатное включение — через AstraIDE
(она умеет править `runtime.cfg`); после сохранения сервис поднимается без перезагрузки.

`/etc/inetd.conf` и другие файлы входят в `firmware_files.lst`/`.hash` (там же
`/etc/ssh/sshd_config`, `/etc/pure-ftpd/*`, `/usr/sbin/sshd`, `/usr/sbin/inetd`),
а `bl_crc_check.sh` раз в сутки спит `86400` и проверяет целостность — правки
файлов прошивки могут быть замечены при обновлении.

  `PermitEmptyPasswords yes`, `AllowUsers root`; ключи хоста `/etc/ssh/ssh_host_*` есть.

## Монтирование диска и просмотр ФС с хоста

Диск — один MBR-раздел QNX6: тип `b1`, старт с сектора 63 (**offset 32256**).
Linux-драйвер `qnx6` (и `qnx4`) — **только чтение**; записать через mount нельзя.

```bash
qm stop 100
lvchange -ay pve/vm-100-disk-0
mount -t qnx6 -o ro,offset=32256 /dev/pve/vm-100-disk-0 /mnt
ls -la /mnt
```

Через nbd (альтернатива): `modprobe nbd max_part=8`, `qemu-nbd -c /dev/nbd0 -f qcow2 -r disk.qcow2`,
`mount -t qnx6 -o ro /dev/nbd0p1 /mnt`. Грабли: `partprobe` нет; незакрытый `/mnt`
перед `qemu-nbd -d` → `Input/output error`; nbd может подняться `RO=1` (лечится
работой с LV напрямую или `blockdev --setrw`).

Снятие «слепка» ФС (делалось так):

```bash
find /mnt -xdev -printf '%y %10s %TY-%Tm-%Td %TH:%TM %p -> %l\n' > /root/regul-fs.txt   # 2258 строк
du -sh /mnt/* 2>/dev/null | sort -h > /root/regul-du.txt
find /mnt -type f -printf '%s %p\n' | sort -rn | head -50 > /root/regul-big.txt
find /mnt -type f | sed 's/.*\.//' | sort | uniq -c | sort -rn | head -30 > /root/regul-ext.txt
find /mnt -maxdepth 2 | grep -i "..."   # точечный поиск
```

Копия конфигов на хост: `cp -a /mnt/etc /mnt/scripts /root/from-vm/`.

## Правка файлов с хоста (raw dd, без записи в qnx6)

Метод: только **замена на такую же длину** (или короче с добивкой пробелами/`#`),
иначе поедут структуры ФС. Обязателен бэкап (`disk.qcow2.bak` или снимок LV).

Примеры, которые уже применялись/планировались:

```bash
# 1) снять «демо-таймер»: заменить && на ||
for O in $(grep -abo "sleep 86400 && /scripts/codesys/stop_ham.sh" /dev/pve/vm-100-disk-0 | cut -d: -f1); do
  printf '||' | dd of=/dev/pve/vm-100-disk-0 bs=1 seek=$((O+12)) count=2 conv=notrunc 2>/dev/null
done

# 2) включить ssh в inetd.conf: 34-символьный маркер -> "ssh" + пробелы
for O in $(grep -abo "#-ssh-disabled from runtime.cfg--#" /dev/pve/vm-100-disk-0 | cut -d: -f1); do
  printf 'ssh%31s' '' | dd of=/dev/pve/vm-100-disk-0 bs=1 seek=$O count=34 conv=notrunc 2>/dev/null
done

# 3) чтобы скрипт не выключил SSH обратно: EnableSQL=1 -> EnableSSH=1 (11 байт)
for O in $(grep -abo "EnableSQL=1" /dev/pve/vm-100-disk-0 | cut -d: -f1); do
  printf 'EnableSSH=1' | dd of=/dev/pve/vm-100-disk-0 bs=1 seek=$O count=11 conv=notrunc 2>/dev/null
done
```

Важно: на диске одна и та же строка встречается несколько раз — «живая» копия +
остатки от `sed -i` и, возможно, копии внутри `.ifs`. Поэтому:

- перед правкой проверить, что строки нет в загрузочных образах
  (`grep -c "ssh-disabled" /mnt/.boot/*.ifs /mnt/ifs/*.ifs` — должно быть `0`),
  иначе правка `.ifs` ломает CRC и VM не загрузится;
- проверять результат через смонтированный RO-вид: если `grep`/`cat` в `/mnt`
  показывают новое значение — попали в живые данные.

Что выяснилось и что сделали:

  (строка root — `root:<hash>::0`, длина блока сохраняется; DES-crypt можно получить

## Патч vmdk на Windows без монтирования (как это работает)

Скрипт: `vmdk-patch.ps1` (в этой же папке).

FDISK/ФС тут не разбираются. VMware Workstation/Player хранит диск как **monolithicSparse**:
512-байтный sparse-заголовок, grain directory/table и **несжатые** 64-КБ grain'ы с данными
гостя. Поэтому содержимое файлов видно в vmdk как обычные байты — его можно искать
`strings`/`grep -a`/байтовым сканером и менять на месте.

- Мы искали **ASCII-якоря** (строку `inetd.conf`, блок `/etc/shadow`, строку таймера)
  и заменяли их байт-в-байт той же длины. Inode, размеры файлов и указатели не трогаются,
  поэтому ФС остаётся целой (QNX6 power-safe, блочных чексумм нет).
- Совпадение искали по **целому многстрочному блоку** — так мы знаем, что данные лежат
  непрерывно (для мелких файлов QNX6 это обычно так).
- В OVA-vmdk (`streamOptimized`) grain'ы **сжаты** — там открытого текста нет; такие образы
  читаются только монтированием (Linux `qnx6`, RO).
- Одинаковые строки встречаются в нескольких копиях (`VirtualBox`/`VMware` скрипты) и в
  «мёртвых» блоках после `sed -i`; лишние замены безвредны, но живую копию надо проверять
  повторным чтением/монтированием.
- Скрипт делает **две фазы**: сначала только читает и собирает смещения, потом пишет.
  Если писать во время последовательного чтения, позиция чтения «уезжает» — проверено,
  часть замен может лечь не туда.
- Только при выключенной ВМ (нет `.lck`, нет `vmware-vmx`), с бэкапом/журналом.
- В PowerShell 5.1 `.ps1` с кириллицей должен быть **UTF-8 с BOM**, иначе парсер ломается.

Примеры (Windows, Git-bash/perl для DES-хэша):

```powershell
# включить ssh (34 символа -> ssh + 31 пробел)
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old '#-ssh-disabled from runtime.cfg--#' -New ('ssh' + (' ' * 31))
# снять таймер (равная длина)
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old 'sleep 86400 &&' -New 'sleep 86400 ||'
# только поиск
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old 'root:*:' -VerifyOnly
```

# Часть 3. Отладка QEMU

Дата: 2026-11-18/19

## Краткий вывод

Апплаенс (QNX 6.5 + CODESYS, OVA из VirtualBox) **работает в VMware/VirtualBox**, но в
QEMU/KVM (Proxmox) сеть не поднимается: драйвер `devn-pcnet` монтируется и показывает
`link=1`, однако **обмена кадрами нет** (rx=0/tx=0). Альтернативный `devnp-e1000` в этой
системе через runtime-mount не загружается вообще (`No such device`). Оставшиеся варианты:
драйвер `devnp-speedo`, запуск `e1000` на старте io-pkt (а не mount'ом) либо вендорская
поддержка KVM.

## 1. Что лежит в OVA (проверено на оригинальном vmdk и pristine `disk.qcow2`)

- Пользовательский `network.cfg` **отсутствует**; `runtime.cfg` содержит только
  `[PlcServices] EnableSQL=1` (без `EnableSSH`).
- Т.е. OVA — «чистый» слепок; IP и SSH в нём не настроены.

## 2. Что появляется после запуска в VMware

При первом запуске AstraIDE находит ПЛК по своему L2-протоколу ESP и **пишет конфиг на диск**:

```
[global]
hostname=localhost

[ip]
port40=192.168.56.25 255.255.255.0      # или port50=192.168.1.188 ...

[routing]
gateway=192.168.56.1
```

и `[PlcServices] EnableSSH=1`.

Подтверждение в логах гостя (`espd-default.log`):

```
16:18:01 port30: ESP_ID_SET_IP from MAC 00:e0:27:36:00:59
16:18:01 Write to config: key=[ip/port50] value=[192.168.1.188 255.255.255.0]
```

Из-за неверных часов гостя (показывает `01.10.2026`, хотя запуск «сегодняшний») эти
записи легко принять за «заводские» — но они появились при запуске после импорта.

**Поэтому** диск VMware-машины отличается от свежего импорта Proxmox: он уже
«провизионен» IDE. Оба диска из одного OVA — расходятся после первого запуска.

## 3. Протокол ESP (AstraIDE ↔ ПЛК), снят tshark

- Кадры **EtherType `0xD000`** — сырой Ethernet II, без IP/TCP; discovery — broadcast
  от ПК (`00:e0:27:...`), ответы — unicast.
- `01` — поиск (discovery); `02` — ответ с инфо: hostname, версия, targetId,
  **gateway**, флаги (`lock:false|true`, `dhcp`, `media`, `redundancy`) — строки через `\0`.
- `03 NN` — запрос инфо интерфейса NN (00..02); `04 NN <имя\0><MAC6><IP4><маска4><флаги4>`
  — ответ: `0400 "port30" 00:0c:29:e4:e9:21 0.0.0.0 0.0.0.0 00 01 03 00`,
  `0401 "port40" …:2b …`, `0402 "port50" …:35 192.168.1.188 255.255.255.0 …`.
  Хвост `00 01 03 00` одинаков (вероятно media/speed/duplex; не доказано).
- `05/06` — SET_IP/ACK; `07/08` — SET_HOSTNAME/ACK; `09/0A` — SET_GATEWAY/ACK;
  `0B` — Wink (без ответа); `0C/0D` — SET_LOCK/ACK. Ответ = запрос+1, статус `u16 LE`
  (0=OK, 1=locked/denied). Полная карта и примеры — `Часть 6`.
- **Отвечают port30/port40/port50** (ethernet1–3), **ecatbus (ethernet0) не отвечает**.
- IDE использует Npcap. Чтение дампа работало без явного повышения прав; отправку
  кадров делали через `wpcap.dll` (`pcap_sendpacket`, `esp-send.ps1`).

## 4. Сетевая модель гостя (isonet)

`/etc/init/network.sh start` → `/etc/init/$REGUL_BOARD/network-itf-mount.sh`
(VirtualBox/VIRTUAL):

```
isonet mount -o pci=0x0,did=0x2000,name=ecatbus -d devn-pcnet.so -s ethercat -n ecatbus0
isonet mount -o pci=0x1,did=0x2000,name=port3    -d devn-pcnet.so -n port30
isonet mount -o pci=0x2,did=0x2000,name=port4    -d devn-pcnet.so -n port40
isonet mount -o pci=0x3,did=0x2000,name=port5    -d devn-pcnet.so -n port50
isonet mount -o pci=0x4,did=0x2000,name=port6    -d devn-pcnet.so -n port60   # 5-й NIC нет — ошибка
```

- `isonet initialize` стартует три стека: `default`, `redundancy`, `ethercat`.
- `isonet updateip` применяет `[ip] portNN=…` из `network.cfg`
  (в логе: `Add ip address for interface portNN as: …`).
- DHCP в `system.main` запускается **только при загрузке с USB** (`BOOT_FROM_USB=1`);
  в обычной загрузке IP берётся из `network.cfg`.

## 5. Результаты в QEMU/KVM (Proxmox)

### pcnet (модель `pcnet`, MAC из OVA)

- Драйвер монтируется: `Command mount complete successfully`, `Up interface port30/40/50`.
- `network.log` (гостевая статистика):
  `port30/40/50 link=1 media_rate=10 rx_bytes=0 rx_pkts=0 tx_bytes=0 tx_pkts=0`.
- На tap'ах хоста: `TX` растёт (кадры от хоста в гостя), `RX=0` (гость не передаёт).
- ESP-демон пишет `Start listening interface...`, но входящих `ESP_ID_*` нет.
- Итог: **линк есть, обмена нет** — несовместимость RX/TX QEMU-pcnet с этим драйвером QNX.
- Опции `speed=10,duplex=1` без `pci=` приводят к `Unable to mount` (pci обязателен);
  линк и без них `=1`.

### e1000 (модель `e1000`, QEMU `8086:100E`, addr 00:12–00:15)

- Драйвер `devnp-e1000.so` присутствует, поддерживает 82540 (function pointers 82540).
- Через `mount -T io-pkt` **не загружается**: `Unable to init devnp-e1000.so: No such device`,
  `pci_attach_device (0): No such device`.
- Пробовали: `did=0x100e` без `vid`; `pci=1..4`; `vid=0x8086,did=0x100e`; десятичные
  `vid=32902,did=4110`; индексы `pci=6..10` — результат один.
- Вероятная причина: devnp-драйверы в QNX грузятся **на старте io-pkt**
  (`io-pkt-v4 -de1000 …`), а не runtime-mount'ом; isonet формирует команду старта сам.
- Вывод: для e1000 нужно либо патчить старт стека, либо иной способ загрузки драйвера.

### Драйверы в образе

`devn-pcnet.so`, `devnp-e1000.so`, `devnp-speedo.so`, `devnp-topcliff.so`,
`devnp-veport.so`, `devnp-shim.so`, `devnp-qtap.so`. Непробованным остался `devnp-speedo`
(AMD PCnet, другая реализация — потенциально лучший RX в QEMU).

## 7. Правила безопасной работы с диском (наши грабли)

- Все правки LV — **только при выключенной VM**. Правка на работающей VM не применяется
  и рискует повредить ФС.
- Байтовые правки: сохранять длину строки (переписывать строку целиком с добивкой
  пробелами) либо подменять равные по длине фрагменты (`&&`→`||`, `did=`→`did=`).
- Одинаковые строки встречаются в нескольких файлах (`VirtualBox` и `VMWare` копии) и в
  «мёртвых» блоках; перед правкой проверять, что строки нет в `.ifs` (иначе ломается CRC
  загрузчика).
- Бэкапы: `disk.qcow2.bak`, нетронутый `/var/tmp/vmware.vmdk`.
- Монтирование: `mount -t qnx6 -o ro,offset=32256 /dev/pve/vm-100-disk-0 /mnt`
  (qnx6 — только чтение; `partprobe` в PVE нет; nbd иногда поднимается RO и «залипает»).

# Часть 4. Учётные данные, порты и настройки соединения

Источники: `Astra.IDE User Guide DPA-302 v2.21` (ru/en), извлечённый текст
(`guide_ru.txt`, `guide_en.txt`).

## Сетевые порты

- **UDP 1740–1743** — broadcast-запросы (обнаружение контроллера, ESP/сканер);
- **TCP 1217** — gateway (служба Communication Settings / Gateway Server);
- **TCP 11740–11743** — подключение к ПЛК (CODESYS-гейтвей).

> Фактически на этом стенде обнаружение/ESP идёт **сырыми Ethernet-кадрами `0xD000`**,
> а не UDP 1740–1743 (см. `Часть 6`). Из TCP реально открыт только **11740**
> (11741–11743, 1217, 4840, 502, 3306 закрыты); FTP 21 и SSH 22 — из `inetd`.

IDE ходит к ПЛК через gateway; локальный gateway — это сам ПК разработчика.

## Авторизация в ПЛК (CODESYS, не ОС)

- До версии 1.7.0.0: учётка **`Administrator`**, пароль по умолчанию **`Administrator`**
  (заводская настройка), после первого входа — принудительная смена пароля.
- Сброс пароля Administrator: через Astra.IDE либо через **сервисный режим** контроллера.
- Опция **Allow Anonymous Login** — разрешает части компонентов (например, OPC UA)
  подключаться без учётных данных.
- Пароль/сертификат можно ставить и на **файл проекта** (не на ОС).
- В проекте есть учётка **Owner** — изначально вход с **пустым паролем**.
- Внимание: логин/пароль ПЛК — только латиница и цифры.

## FTP (порт 21)

- Учётки по умолчанию в `etc/ftp.userlist`:
  - `plclogs` — доступ к каталогу логов (`/logs`), обычно ReadOnly;
  - `plcuser` — доступ к пользовательскому каталогу (`/`), ReadWrite.
- В примере конфигурации у обеих `Password=` **пустой**; в разделе про выгрузку
  журнала указано: **логин `plclogs`, пароль `service`**.
- `Access` = `ReadWrite`/`ReadOnly`; прочие параметры: `HomeDir`, `Password`,
  `DownloadBandwidth`, `UploadBandwidth`, `AllowedClientIPs`, `DeniedClientIPs`,
  `TimeRestrictions`. Изменения применяются за 10–20 с (fwatch).
- TLS настраивается в `etc/plc.cfg`, секция `[FTP]`, параметр `TLS` (0/1/2);
  диапазон пассивных портов — `PassivePortRange`.
- Включение FTP — `[PlcServices] EnableFTP=1` в `etc/runtime.cfg`.

## MySQL (встроенная БД)

- Локальное подключение — **пустой пароль**.
- Удалённое подключение — пароль по умолчанию **`6ViQgjps`**.
- Смена: `SET PASSWORD FOR 'user'@'%' = PASSWORD('...');`
- Ограничение размера БД — `plc.cfg`, секция `[Database]`, `MaxDbSize` (МБ).
- Включение/выключение SQL — `[PlcServices] EnableSQL` в `runtime.cfg`.

## Сетевые настройки (Network Scanner)

- Меню **Tools → Network Scanner**: выбрать сетевой интерфейс → **Rescan**;
  новые контроллеры подсвечиваются зелёным.
- В области Settings показываются символьное имя PLC и адрес gateway.
- **Static address**: поля IP и Mask — задать адрес и маску.
- **Gateway** — задаётся один на все сетевые интерфейсы (кнопка Write).
- Есть **Export/Import** настроек (удобно хранить профили площадок).
- Кнопка **Settings Lock** — защита от случайного изменения настроек.
- Дополнительные IP/маски — через alias на интерфейсе.
- Внимание: **обновление прошивки сбрасывает настройки к заводским** (включая IP) —
  сохраняйте/восстанавливайте конфигурацию.

## Сервисный режим (сброс к заводским)

- Нужен, когда подключиться через Astra.IDE невозможно.
- На R200/R500/R600: RUN/STOP + KEY; на R400 — через встроенный сенсорный экран.
- Пункт меню 1 — **Factory Reset** (сброс пароля Administrator, приложений и настроек).
- Вход в сервисный режим при загрузке можно **запретить** (соответствующая опция).
- После сброса — вход с заводскими `Administrator`/`Administrator`.

# Часть 5. Инструменты и правила

## `vmdk-patch.ps1` — правка образа без монтирования

Скрипт ищет ASCII-подстроку в контейнере (vmdk/qcow2/raw) и заменяет её на строку
**той же длины**. ФС не разбирается; работает за счёт того, что VMware monolithicSparse
хранит данные гостя несжатыми (в OVA streamOptimized — сжаты, там не сработает).

```powershell
# поиск с контекстом
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old 'root:*:' -VerifyOnly
# включить ssh (34 символа -> "ssh" + 31 пробел)
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old '#-ssh-disabled from runtime.cfg--#' -New ('ssh' + (' ' * 31))
# снять демо-таймер (равная длина)
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old 'sleep 86400 &&' -New 'sleep 86400 ||'
```

Правила: только при выключенной ВМ (нет `.lck`, нет `vmware-vmx`); длины совпадают
(или `-PadWithSpaces`); двухфазный проход (чтение → запись), иначе «уезжает» позиция
чтения; проверка результата повторным поиском/монтированием; `.ps1` с кириллицей —
UTF-8 с BOM.

Ограничения:
- Это не ФС-редактор: размер файла/inode не меняются. Добавить пользователя/строку
  в `UserDatabase.csv`/`GroupDatabase.csv` им нельзя — для этого SFTP/SSH и
  `userdb-checksum.ps1`; после правки CSV пересчитать `Checksum`.
- Заменяются **все** вхождения `Old`, включая мёртвые копии и копии в `.ifs`.
  Перед патчем проверить `grep -c` по `.ifs`; иначе можно сломать CRC загрузчика.
- Правки `/etc/shadow`, `/etc/inetd.conf` и др. могут ловиться
  `firmware_files.hash`/`bl_crc_check.sh` (проверка целостности прошивки).
- Для `*.fwe`/зашифрованных контейнеров не годится; для CSV с изменением длины —
  тоже.

## `connect-plc.ps1` — SSH к контроллеру

```powershell
.\connect-plc.ps1
.\connect-plc.ps1 -Ip 192.168.1.188 -Command "id; uname -a"
```

Внутри — legacy-алгоритмы (`ssh-rsa`, `hmac-sha1/md5`, `dh-group14-sha1`), иначе
современный OpenSSH отказывается от старого sshd.

## SSH без интерактивного ввода (Windows OpenSSH 9.5)

`ssh` не читает пароль из stdin, но Windows-сборка поддерживает `SSH_ASKPASS`:
создать `askpass.cmd` с `@echo <пароль>`, задать `SSH_ASKPASS`,
`SSH_ASKPASS_REQUIRE=force`, `DISPLAY=localhost:0` и legacy-алгоритмы
(`HostKeyAlgorithms=+ssh-rsa,ssh-dss`, `KexAlgorithms=+diffie-hellman-group14-sha1`,
`MACs=+hmac-sha1`). Так выполняются команды и копируются файлы.

В госте **нет бинарника `scp`**, но **SFTP-подсистема работает**
(`/usr/libexec/sftp-server`, `Subsystem sftp internal-sftp`):
- современный `scp` (режим SFTP, **без `-O`**) и `sftp` работают;
- legacy `scp -O` падает (`ksh: scp: cannot execute`);
- `sftp -b` включает BatchMode и отключает askpass — команды лучше подавать
  через stdin (`"ls ...`nbye" | sftp ...`).

`curl` без SFTP. Для бинарного копирования также годится `ssh "cat /path"` с чтением
`Process.StandardOutput.BaseStream` (`plc-pull.ps1`); обычный PowerShell-пайплайн
портит байты. Так сняты ключи, CSV учёток и конфиги (см. `plc-dump/`).

## Клиенты SFTP/SCP для Windows

- **WinSCP** (GUI + `winscp.com`) — рекомендуется: SFTP, сохранённые сессии,
  синхронизация, скрипты; понимает legacy `ssh-rsa`/`dh-group14-sha1`.
  Использовать **SFTP**, не SCP (бинаря `scp` на ПЛК нет).
- **PuTTY (`pscp`/`plink`)** — лёгкий CLI: `pscp -sftp -pw ...`, `plink -ssh -pw ...`;
  legacy-алгоритмы поддерживаются.
- **Встроенный OpenSSH** — уже есть: `scp`/`sftp` с
  `HostKeyAlgorithms=+ssh-rsa`, `KexAlgorithms=+diffie-hellman-group14-sha1`,
  `MACs=+hmac-sha1` и `SSH_ASKPASS` (см. выше).
- FileZilla — GUI SFTP, но свежие версии могут не включить `ssh-rsa`; MobaXterm —
  GUI+SFTP+терминал, тяжелее. Termius не советую (старые алгоритмы часто отключены).

Проверено: **WinSCP 6.x** (`C:\Program Files (x86)\WinSCP\WinSCP.com`) — SFTP,
`root@192.168.1.188`, пароль, `-hostkey=*`; legacy-алгоритмы работают без правок:
```
winscp.com /ini=nul /command "open sftp://root:regul123@192.168.1.188/ -hostkey=*" `
  "ls /mnt/user/codesys/etc" "get /mnt/user/codesys/etc/plc.cfg C:\temp\plc.cfg" "exit"
```
В GUI: New Site → File protocol **SFTP**, Host `192.168.1.188`, Port `22`,
User `root`, Password `regul123`; хост-ключ принять. Режим SCP не использовать
(бинаря `scp` на ПЛК нет).

## `esp-send.ps1` — отправка ESP-кадров (Npcap)

Собирает Ethernet II кадр (dst/src MAC, EtherType `0xD000`, payload, добивка нулями
до 60 байт) и отправляет через `pcap_sendpacket` (`C:\Windows\System32\Npcap\wpcap.dll`).
Это **не TCP/IP**, а сырой L2; устройство — из `dumpcap -D`.

```powershell
# discovery (broadcast)
.\esp-send.ps1 -PayloadHex '01'
# SET_IP для port40: idx=1, 192.168.0.100/24
.\esp-send.ps1 -DstMac 00:0c:29:e4:e9:21 -PayloadHex '0501c0a80064ffffff00'
# SET_HOSTNAME "localhost"
.\esp-send.ps1 -DstMac 00:0c:29:e4:e9:21 -PayloadHex '076c6f63616c686f737400'
# SET_LOCK
.\esp-send.ps1 -DstMac 00:0c:29:e4:e9:21 -PayloadHex '0c'
```

Устройство по умолчанию: `\Device\NPF_{D8BEBB9E-D166-4688-B59A-59FA59B04CF3}`
(Ethernet 2, 192.168.1.121, MAC `00:e0:27:36:00:59`); при смене адаптера — править
параметр `-Device`.

## `userdb-checksum.ps1` — Checksum для `.UserDatabase.csv` / `.GroupDatabase.csv`

CRC-32 (полином `0xEDB88320`, init/xor `0xFFFFFFFF`) по конкатенации всех строк
**без CRLF**, исключая строку `Checksum`. Это ровно то, что делает рантайм
(строки пишутся с CRLF, но CRC считается по тексту строк без переводов).

```powershell
# только проверить
.\userdb-checksum.ps1 -Path .\UserDatabase.csv -VerifyOnly
# пересчитать Checksum после правки
.\userdb-checksum.ps1 -Path .\UserDatabase.csv
```

## Общие правила работ

1. Правки диска — только при выключенной ВМ; бэкап (`disk.qcow2.bak`, `*.vmdk.bak`).

3. Проверять, нет ли строки в `.ifs` (CRC загрузчика), прежде чем патчить все вхождения.
4. Помнить про «мёртвые» копии строк после `sed -i` и копии в `VirtualBox`/`VMWare`-скриптах.
5. В госте нет `reboot`/`shutdown` — перезагрузка только через Power Off/On ВМ.
6. Часы гостя могут быть неверными (в логах «01.10.2026») — ориентироваться на время суток/uptime.

## 6.1. Формат ESP

- Ethernet II, EtherType `0xD000`, без IP/TCP. Минимальный кадр добивается нулями
  до 60 байт; ПЛК корректно разбирает и такие (проверено).
- **Ответ = опкод запроса + 1**. В ответе статус `u16 LE`: `00 00` = OK,
  `01 00` = locked/denied.
- Для `05` ответ `06 <idx> <status u16>`; для `07/09/0C` — `08/0A/0D <status u16>`.

| Req | Resp | Имя (`espd-default.log`) | Payload запроса |
|---|---|---|---|
| `01` | `02` | GET_HOST_INFO (discovery) | — |
| `03` | `04` | GET_INTERFACE_INFO | `NN` (00..02) |
| `05` | `06` | SET_IP | `idx, IP4, маска4, 00` |
| `07` | `08` | SET_HOSTNAME | ASCII `name\0` |
| `09` | `0A` | SET_GATEWAY | ASCII `ip\0` |
| `0B` | — | Wink | — |
| `0C` | `0D` | SET_LOCK | — |

Ответ `02` (строки через `\0`, в конце два `00`):
```
02 03
"localhost" 0
"1.7.2.6 For non-commercial use only" 0
"0x0B_R500_71_W[VirtualBox-VIRTUAL]" 0
"192.168.1.1" 0            # gateway; пусто, если не задан
"lock:true|false" 0 "dhcp:true" 0 "media:true" 0 "redundancy:true" 0 0
```

Ответ `04` (пример для port50):
```
04 02 "port50\0" 00:0c:29:e4:e9:35 192.168.1.188 255.255.255.0 00 01 03 00
```
Хвост `00 01 03 00` одинаков для всех портов; вероятно media/speed/duplex,
но не доказано.

## 6.2. SET_IP / gateway / hostname / lock (проверено на живом ПЛК)

- SET_IP: `05 01 C0 A8 00 64 FF FF FF 00` → `06 01 00 00`.
  Лог: `Write to config: key=[ip/port40] value=[192.168.0.100 255.255.255.0]`,
  затем `isonet updateip`: `Add ip address for interface port40 as: 192.168.0.100 255.255.255.0`.
  port50 (`192.168.1.188/24`) не меняется.
- SET_GATEWAY: `09 "192.168.1.2\0"` → `0A 00 00`; затем `09 "192.168.1.1\0"` →
  `0A 00 00`. Лог: `key=[routing/gateway] value=[...]`.
- SET_HOSTNAME: `07 "localhost\0"` → `08 00 00`. IDE шлёт его перед каждым Write.
- SET_LOCK: `0C` → `0D 00 00`; лог:
  `Write to config: key=[global/remote-config] value=[deny] prev_value=[null]`.
  В discovery сразу `lock:true`.
- **Под локом** `07 "localhost\0"` → **`08 01 00`** (status 1), лог:
  `Write to config: key=[global/hostname] value=[localhost] failed: locked`.
  Т.е. лок реально блокирует ESP-запись (не только UI).
- `0B` = **Wink** (лог `port30: Wink`), ответа нет; это не unlock.
- Отдельного ESP-опкода разблокировки нет. Снятие — только правкой `network.cfg`
  через CODESYS (AstraIDE) с логином `admin`; после записи файла discovery сразу
  показывает `lock:false`, перезагрузка не нужна.
- Управляющий кадр `05/07/09/0C` IDE адресует на MAC одного из портов (обычно port30),
  а целевой интерфейс задаётся **индексом в payload**. Принимающий порт может быть
  любым (в одном опыте принят port30 → применён port40; в другом принят port40 →
  применён port50).

```
[ip]
```

## 6.4. Security screen на TCP 11740

- Рамкировка блока: `00 01 17 E8` + `u32 LE` длина (включая 8-байтный заголовок).
- Далее 20-байтный адресный блок (порт 11740, IP ПЛК, локальный адрес) и сообщение:
  `01 81 | chid u16 | seq u32 | ack u32 | len u32 | crc32 | 55 CD 10 00 | ... | payload`
  (`01 81` — запрос, `01 01` — ответ; `chid` свой у каждого канала/операции).
- Handshake: greeting (16 байт) → device info → клиент представляется
  (`Astra.IDE_V1.7.2.2`, `WIN-VQQ38AFS7EM`, `3.5.17.30`) → сервер даёт **nonce**
  (`21 84 80 00 <u32>`) и уровень безопасности → клиент запрашивает ключ →
  сервер отдаёт **RSA-2048 public key** (`27 C4 83 00` + PEM `-----BEGIN PUBLIC KEY-----`).
- Логин: `10 06 "admin\0"` + тег `11/12 80 82 00` + **256-байтная RSA-криптограмма**.
  Каждый логин даёт разный шифртекст; nonce исключает replay.
- Сертификат `CmpSecureChannel`: `CN=localhost`, `O=Vendor: Prosoft Systems`,
  `OU=Device: R500 71-W`, SAN `localhost`, срок `01.10.2026–31.10.2026 15:45:23Z`;
  компоненты `CmpApp`, `CmpSecureChannel`, `CmpWebServer`.
- **TLS на 11740 нет.** Всё, кроме поля пароля, — plaintext: листинги каталогов,
  имена и содержимое файлов (`runtime.cfg`, `network.cfg`, `plc.cfg`, `ftp.userlist`,
  `host_key.pub` и т.д.). CRC32 — не криптография.
- Асимметричный ключ логина задан в `/mnt/user/codesys/etc/.ExtConfig1.cfg`:
  `[CmpUserMgr] SECURITY.UserMgmtEnforce=YES`, `AsymmetricAuthKey=4b9836f4…`
  (файл `/mnt/user/.codesys/.pki/own/key/4b9836f4….key`),
  `[CmpSecureChannel] CertificateHash=5e5a8df9…` (сертификат `own/cert/5e5a….der`;
  его ключ `/etc/ssl/private/key.pem` — отдельная пара TLS/устройства).
- Ключ `AsymmetricAuthKey` **ротируется**: в сессии 17:31 в handshake был другой
  ключ (его уже нет на диске), а `4b…` и `.ExtConfig1.cfg` созданы 18.11 19:07.
  Т.е. расшифровать можно только логины, снятые при текущем ключе; после ротации
  старые блобы нечитаемы, старого ключа на диске нет.
- Расшифровка текущего блоба ключом `4b…` (PKCS#1 v1.5) даёт **234 байта
  непрозрачных данных**, не ASCII-пароль: вероятно, хэш/сессионная структура.
  `MD5/SHA1/SHA256("12345Qwert")` и nonce в открытом виде не найдены.
- Практика: зная `admin`/`12345Qwert`, можно читать/писать файлы ПЛК по 11740;
  on-path наблюдатель видит всё в легитимной сессии и без приватного ключа.

## 6.5. Учётные записи и права CODESYS (не MariaDB)

- Пользователи хранятся **не в MariaDB**, а в CSV в `/mnt/user/.codesys/`
  (пути заданы в `/codesys/ExtConfig0.cfg`):
  - `.UserDatabase.csv` — `UserDB,FileVersion,2` и записи
    `u,<name>,0x00002000,3,<salt 8 байт>,<hash 64 байта>,32768,8,1`.
    Изначально был только `admin`; в тесте добавлены `oleg`, `oleg2`, `testuser`.
    Поле `3` одинаково у всех — это **не id**, а тип/схема аутентификации;
    `0x00002000` — флаги.
  - `.GroupDatabase.csv` — `g,<group>,0x00000000` + строки членства
    `a,<group>,u=<user>,g=<subgroup>`; участники дописываются в ту же строку
    (`a,Administrator,u=admin,u=oleg,g=Developer`). Группы наследуются:
    `Administrator → Developer → Service → Watch`.
  - `.UserMgmtRightsDB.csv` — права групп по объектам: у `Administrator` полный
    доступ к `Device` и `/`; `Service/Developer` ограничены; `Watch` — чтение.
- Конфиг: `/mnt/user/codesys/etc/.ExtConfig1.cfg`:
  `[CmpUserMgr] SECURITY.UserMgmtEnforce=YES`,
  `AsymmetricAuthKey=4b9836f4…`; `[CmpSecureChannel] CertificateHash=5e5a8df9…`.
- Пароль хранится как **scrypt**: `salt` = 8 байт (`c5cb3206438ba6a3`),
  `dkLen` = 64 байта, параметры `N=32768, r=8, p=1` — это и есть поля `32768,8,1`.
  Проверено (OpenSSL 3.5) на `admin`, `oleg`, `oleg2`, `testuser`: хэши совпадают
  байт-в-байт (пароли `12345Qwert` / `Qwert12345` / `Test12345`).

  ```powershell
  openssl kdf -keylen 64 -kdfopt pass:12345Qwert `
    -kdfopt hexsalt:c5cb3206438ba6a3 `
    -kdfopt n:32768 -kdfopt r:8 -kdfopt p:1 SCRYPT
  ```

  Запись: `u,<name>,<flags>,<id>,<salt>,<hash>,<N>,<r>,<p>`; `0x00002000` — флаги,
  `3` — тип/схема, в конце файла `Checksum,0x%08x`.
  **Checksum = стандартный CRC-32** (полином `0xEDB88320`, init `0xFFFFFFFF`,
  xorout `0xFFFFFFFF`) по конкатенации всех строк **без CRLF** и **без строки
  `Checksum`**. Проверено на UserDB/GroupDB до/после добавления пользователей —
  совпадает байт-в-байт. Т.е. CRC считается по тексту строк, а не по файлу с
  переводами строк (поэтому обычный CRC файла не сходился). В бинаре это видно:
  таблица `0x084A0800`, цикл `0x817C2A0`, init `0x817C264`, final `not`,
  writer `0x83EEBF0`, проверка `0x83EF0F2` (`File CRC not valid.`).
  Пересчёт/проверка: `userdb-checksum.ps1 -Path <csv> [-VerifyOnly]`.
  Проверено end-to-end: в копию UserDB добавлен `offline` (scrypt), в GroupDB —
  `a,Watch,u=offline`, Checksum пересчитан и валиден (`plc-dump/test/`).
  Практически: при утечке диска хэш можно брутить офлайн (scrypt ~32 МБ на попытку;
  слабый пароль подбирается), а зная пароль — генерировать новый хэш и менять
  пользователей правкой CSV (нужно пересчитать Checksum).
- MariaDB (`regul`) — это **логи**, не учётки: БД `information_schema`, `mysql`,
  `performance_schema`, `regul`; пользователи БД `root@localhost` (пароль из
  бэкап-скрипта), `user@%`, `user@localhost`, `psmysql@localhost`. Это не CODESYS.
- Скопировано в `plc-dump/`: `UserDatabase.csv`, `GroupDatabase.csv`,
  `UserMgmtRightsDB.csv`, `ExtConfig1.cfg`, `ExtConfig0.cfg`, ключи `4b/a4`,
  `blob.bin/txt` (расшифрованный логин текущего ключа).

## 6.6. Безопасность ESP и лока

- ESP полностью **без аутентификации** и без anti-replay: любой в том же L2 может
  слать `05/07/09` (менять IP/hostname/gateway) и `0C` (ставить лок).
- Лок (`global/remote-config=deny`) блокирует ESP-запись (status 1), но снимается
  только через CODESYS с паролем → **DoS-вектор**: атакующий лочит контроллер,
  админ вынужден идти в IDE/AstraIDE.
- «Settings Lock» в UI — это тот же флаг `remote-config`, отдельной защиты нет.

## 6.7. Открытые вопросы (по ESP/11740)

- Есть ли ESP-опкод разблокировки (кандидаты `0E/0F`); не проверялось.
- Блокирует ли лок также `05`/`09` (ожидается `06 01 01 00` / `0A 01 00`); проверено
  только `07` → `08 01 00`.
- Что означают поля `00 01 03 00` в ответе `04` и хвостовой `00` в `05`.
- Переживают ли лок и адреса Power Off/On (в `network.cfg` на диске — да, но reboot
  не проверяли).
- ~~Состав учёток CODESYS~~ — разобрано (6.5): только `admin`, группы
  Watch/Service/Developer/Administrator, пароль — scrypt (N=32768,r=8,p=1).

- Чтобы получить консоль, нужно добавить `tinit`/`getty` на `/dev/con*` или

  update-пакете/basefs или создаётся при обновлении). `etfs-init.sh` (factory
  init) вызывает его для ETFS; `update_raw_nand.sh` пишет MLO/barebox/IFS по
  offset'ам (ARM OMAP3530); `firmware_download.sh` — это прошивки MCU/FPGA из
  `lib/firmware/<dev>/firmware.bin`, не главный `.fwe`.
- `download_regul.sh` качает `.fwe` с вендорского FTP `ogis-bs`
  (`anonymous`/`123`, `/Firmware/Regul/Versions/<ver>/fwi/`), а
  `download_and_make.sh` вызывает `make_regul_hd.sh` — сборку HDD-образа из
  `.fwe` (на ПЛК скрипт отсутствует; вероятно, вендорский инструмент).
- В конце `.fwe` — **plaintext-футер** (32 байта):
  `\n[firmware_end]\nsize=0000001537\n`. Т.е. зашифрован только payload, а футер
  снаружи; длина payload (от offset 16 до футера) не кратна 16/8 → вероятно
  stream cipher (AES-CTR/OFB/CFB) или нестандартный контейнер.
- Попытки расшифровать payload паролями `pscrypt`/`pskpdacrypt` (из
  `/scripts/pass.sh`), а также `regul`, `regul123`, `firmware`, `RegulFw`, `ogis`,
  `123` и шифрами AES-256-CBC/CTR/OFB/CFB, 3DES, ChaCha20 (md5/sha256/sha1)
  осмысленного результата **не дали**. Ключ/пароль не бэкапный и не в rootfs.
- В текущем rootfs **нет** `updateFW.sh`, `make_regul_hd.sh`, `fw.key`.
  В vmdk (`...-disk1.vmdk`, 631 МБ) встречаются только **имена** в листингах/
  свободных блоках (`/scripts/make_regul_hd.sh`, `/etc/openssl/fw.key`,
  `updateFW`), но не их содержимое; `openssl enc` в vmdk — это `backup.sh`,
  не апдейтер.
- Зато в слепке Proxmox-диска (`regul-fs.txt`) **есть**:
  - `/mnt/scripts/make_regul_hd.sh` — 2431 байт;
  - `/mnt/ifs/` — реальные образы (`REGUL_VMWare.ifs`, `REGUL_Lippert_ECO2*.ifs`,
    `KTM_image_CPC304_LX800.ifs`);
  - `/mnt/scripts/pass.sh`, `/mnt/scripts/update/*`, `/mnt/etc/firmware_files.lst`
    и `.hash`.
  `updateFW.sh` и `fw.key` в этом списке **отсутствуют**.
- В текущей VMware-копии `/etc/firmware_files.lst` всё ещё перечисляет
  `/etc/openssl/fw.key`, `/scripts/make_regul_hd.sh`, `/scripts/updateFW.sh`,
  но самих файлов нет; `/etc/firmware_files.hash` содержит MD5
  `make_regul_hd.sh` (`fc64ab95ebdebe4680382cf4334ea135`) и `pass.sh`
  (`9da579b538b5aa9976e466855afec932`). Т.е. VMware-образ урезан/модифицирован
  относительно Proxmox-слепка; `make_regul_hd.sh` надо забрать с Proxmox-диска.
- `make_regul_hd.sh` забран с Proxmox, MD5 совпал. Это **не** распаковщик:
  он размечает `/dev/hd1` (QNX6 root 400 МБ + user), ставит `dloader`,
  делает `mkqnx6fs` и вызывает `/scripts/updateFW.sh $1 /hd1 keep`.
  Вся работа с `.fwe` — в `updateFW.sh`.
- `pass.sh` — только пароль бэкапа (`pscrypt`/`pskpdacrypt`), к `.fwe` отношения
  не имеет (проверяли расшифровку).
- `updateFW.sh`/`fw.key` в `regul-fs.txt` **отсутствуют**; в `firmware_files.lst`
  они есть, в `firmware_files.hash` — нет. Вероятно, они лежат в factory/update-
  пакете, а не в установленном rootfs.
- В `/basefs/.boot` только `VirtualBox_VIRTUAL.ifs` и `REGUL_VirtualBox.ifs`;
  `/ifs` (образы реального железа) отсутствует. VM — урезанный VirtualBox-демо-
  образ; полноценный апдейтер/ключ, вероятно, есть в OVA/на Proxmox-диске или
  в вендорском пакете, а не в этой VM.
- Для ARM пишется raw NAND; для x86/VMware — HDD/ETFS-образ (`make_regul_hd.sh`).

## 7.4. Root-пароль

- Проверка DES (`openssl passwd -crypt`):
  - `/etc/oshadow` root `abWKPtL.M8W9Q` (salt `ab`) → **`regul123`**;
  - `/etc/shadow` root `O0fiWueOsxV5w` (salt `O0`) → **`regul123`**.
  Текущий root-пароль — `regul123` (подтверждено).
- Заводской root в исходном образе — `*` (locked), стандартного пароля нет.
  Строка `oshadow` — `root:abWKPtL.M8W9Q::0`, ровно формат нашего патча
  (`root:*:1459159315:0:0` → `root:abWKPtL.M8W9Q::0`), т.е. `oshadow` был
  пропатчен вместе с `shadow`, а не является заводским хэшем.
- `opasswd` (2016): `rcodesys`/`rlog` — FTP-only (`/sbin/ftplogin`), без
  shadow-хэшей. `oshadow` содержит только root/plclogs/plcuser; `plclogs`=`service`
  (проверено), `plcuser` — пустой по руководству (фактический FTP-логин не прошёл).
- Перебор **заводского** root-пароля бессмысленен — его нет (locked). Для другого
  устройства с DES-хэшем подбор возможен (`openssl passwd -crypt` + словарь), но
  здесь текущий пароль уже известен.

## 7.6. Формат пользовательского бэкапа (`user_backup.sh`)

- `*.dat` (public backup):
  1. первые **65536 байт** — metadata: `gzip` от `meta.tar` (targetId, hostname,
     version, osname, com_module) + SHA1/SHA224 всего 64-КБ блока в последних
     20/28 байтах;
  2. далее `openssl enc -aes-256-cbc -pass $(get_pass)` от `tar.gz` каталога
     `/mnt/user` (исключены `backup update restore usb* sd* logs etc/host_key.pub`);
  3. в конце — SHA1/SHA224 всего файла (20/28 байт).
- `users.dat` (private): `tar czp .codesys | openssl enc -aes-256-cbc -pass ...`
  — там `.codesys` (PKI-ключи, user DB), **без** 64-КБ metadata.
- `get_pass` (`/scripts/pass.sh`): `pass:pscrypt`, для `KPDA_18` —
  `pass:pskpdacrypt`. OpenSSL 1.0.0e, `enc` по умолчанию MD5 (`-md md5`).
- Публичный архив — это `/mnt/user`, а **не rootfs**: `updateFW.sh`/`fw.key`
  в обычном user backup, скорее всего, не будет; но будут `codesys/etc`,
  `cert`, проект, а в `users.dat` — приватные ключи/учётки.
- Распаковка: `open-backup.ps1` (Часть 5). В metadata 1.6.5.16 поля `osname`
  нет (в 1.7.2.6 скрипт его добавляет); пароль определяется перебором
  `pscrypt`/`pskpdacrypt`.

## 7.8 Если что забыл


Как распаковывал .dat
Структура:

[64 КБ metadata: gzip(meta.tar) + SHA1/SHA224 в конце]
[openssl enc -aes-256-cbc (tar.gz от /mnt/user)]
[SHA1/SHA224 всего файла, 20/28 байт]
Алгоритм:

Проверить SHA1 тела [0 .. len-21] с последними 20 байтами (или SHA224 — 28).
Взять первые 64 КБ → meta.tar (targetId, version, com_module, backupparts…).
Payload [65536 .. len-digest-1] → openssl enc -d -aes-256-cbc -md md5 -pass pass:pscrypt (для KPDA_18 — pskpdacrypt).
Полученный tar.gz распаковать в public/.
Скрипт сохранён: C:\Users\user\Documents\opencode\open-backup.ps1. Проверен на R500-бэкапе — metadata и полная распаковка работают.

# только метаданные (быстро проверить USER/BASE/ALL)
.\open-backup.ps1 -Path .\backup\PLC_xxx.dat -MetadataOnly

# полный разбор (pscrypt/pskpdacrypt подбирается сам)
.\open-backup.ps1 -Path .\backup\PLC_xxx.dat

# если отдельно есть users.dat (приватная .codesys)
.\open-backup.ps1 -Path .\backup\PLC_xxx.dat -UsersDat .\backup\users.dat
По умолчанию распаковывает в backup\extract-<имя>, ищет fw.key, updateFW.sh, make_regul_hd.sh, .fwe, .ifs, .codesys, UserMgmtDB, ключи/сертификаты. Предупреждение tar про mnt/user/codesys/logs — это symlink, нормально.

Если найдёшь full/base backup — сначала -MetadataOnly; если там backupparts=BASE/ALL, запускаем полный разбор и ищем ключ/апдейтер.



vmdk-patch.ps1 — это «grep + dd» по сырому образу диска, без монтирования ФС и без понимания QNX6.

Что делает
Ищет ASCII-подстроку -Old в vmdk/qcow2/raw/img и заменяет её на -New той же длины.
Работает в два прохода: сначала только читает 8-МБ блоками и собирает смещения, потом открывает файл на запись и пишет по ним. Если писать во время чтения, позиция чтения «уезжает» — на этих граблях уже стояли.
Байты ↔ символы через Latin-1 (1:1), поэтому подходят ASCII/байтовые строки; кириллицу лучше не использовать.
Находит все вхождения, включая живую копию, мёртвые копии после sed -i и копии в .ifs.
Параметры
# только поиск с контекстом
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old 'root:*:' -VerifyOnly

# включить ssh в inetd.conf: 34 символа -> "ssh" + 31 пробел
.\vmdk-patch.ps1 -Path .\disk1.vmdk `
  -Old '#-ssh-disabled from runtime.cfg--#' -New ('ssh' + (' ' * 31))

# снять демо-таймер (равная длина)
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old 'sleep 86400 &&' -New 'sleep 86400 ||'

# посмотреть, что будет заменено, но не писать
.\vmdk-patch.ps1 -Path .\disk1.vmdk -Old '...' -New '...' -DryRun
-PadWithSpaces разрешает замену более короткой строкой с добивкой пробелами до длины Old; -Context задаёт размер контекста.

Ограничения
Это не редактор ФС: размер файла и inode не меняются, поэтому добавить пользователя/строку в UserDatabase.csv им нельзя. Для этого — SFTP/SSH, а после правки CSV — userdb-checksum.ps1 (пересчёт Checksum).
Патчить только при выключенной ВМ, без .lck/vmware-vmx, с бэкапом.
Работает для VMware monolithicSparse (наш ...-disk1.vmdk), но не для OVA streamOptimized/сжатых qcow2 — там данные в grains сжаты.
Может зацепить .ifs/мёртвые копии: перед массовой заменой проверь grep -c по .ifs, иначе CRC загрузчика.
Правки /etc/shadow, /etc/inetd.conf и т.п. могут обнаружиться firmware_files.hash/bl_crc_check.sh — это проверка целостности прошивки.
